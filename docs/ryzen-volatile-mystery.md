# Почему на Ryzen `volatile` перестал тормозить?

## Загадка

### Контекст

Восстановил код C с `volatile` (для наглядности параллельных вычислений).
В предыдущих прогонах (i3-7100) `volatile` в C давал ~50 µs против ~15 µs у Rust с `black_box` и Go-контроля.
Разница в 3x — то, что и требовалось для наглядности.

### Что изменилось

Перешёл на динамическую загрузку `.so` через `dlopen`/`dlsym` (раньше была статическая линковка через). Сборка та же: `gcc -shared -fPIC -O2`. Прогнал на Ryzen AI 7 350:

```
BenchmarkAdd-16            12007 ns   ← C + volatile
BenchmarkSub-16            12073 ns   ← Rust + black_box
BenchmarkGoControlShot-16  11914 ns   ← чистый Go, без C
```

### Симптом

Все три числа совпали с точностью до 1%. `volatile`-надбавка исчезла!

```asm
1144: mov -0x8(%rbp),%rcx

```

- Счётчик: `edx = 0x2710` = 10000, уменьшается на 1.
- Одна итерация = **один раунд** xorshift.
- Состояние хранится в локальной переменной на стеке `-0x8(%rbp)`.
- После каждого из трёх шагов раунда делается запись в память и чтение из памяти.
- То есть за раунд: 6 чтений и 3 записи в стек.

### 2. `sub`: цикл развёрнут на 2, состояние в регистрах

```asm
1110: mov %rdx,%rsi
1113: shl $0xd,%rsi
1117: xor %rdx,%rsi
111a: mov %rsi,%rdx
111d: shr $0x11,%rdx
1121: xor %rsi,%rdx
1124: mov %rdx,%rsi
1127: shl $0x5,%rsi
112b: xor %rdx,%rsi
112e: mov %rsi,%rdx
; ... и сразу второй такой же раунд ...
114c: add $0xfffffffe,%ecx   ; это -2
114f: jne 1110
```

- Счётчик: `ecx = 0x2710` = 10000, но уменьшается на **2**.
- Одна итерация = **два раунда** xorshift.
- Итераций: 5000, но раундов всё равно 10000.
- Состояние целиком в регистрах `rdx`/`rsi`.
- В память пишется только после цикла, внутри цикла нет `load/store` состояния.

### Итог

**Разница в замедляющем цикле:**

| | `add` | `sub` |
|---|---|---|
| Раундов xorshift | 10000 | 10000 |
| Итераций цикла | 10000 | 5000 |
| Развёртка | нет | на 2 |
| Состояние | в стеке `-8(%rbp)` | в регистрах `rdx/rsi` |
| Обращения к памяти в цикле | много | почти нет |

То есть оба цикла делают одинаковое число xorshift-раундов, но `sub`-версия эффективнее: она вдвое меньше крутит цикл и не трогает память на каждом шаге. Поэтому `add`-цикл медленнее и «замедляет» сильнее. Ещё в `add` перед циклом есть пачка выравнивающих `nop`, а в `sub` только `xchg %ax,%ax`.


C-код должен тормозить!

## Разгадка

volatile-цикл xorshift на Ryzen показывает нулевую надбавку к времени, потому что Zen 5 использует memory renaming — механизм, впервые появившийся в Zen 2. Он распознаёт паттерн load → ALU → store по одному адресу и переименовывает его в физический регистр, делая задержку load нулевой. На Intel Skylake такого механизма нет, поэтому volatile-версия платит полную цену store-to-load forwarding (~5 циклов за операцию).

## «На пальцах»

### Короткая версия:

> `volatile` запрещает **компилятору** держать переменную в регистре.  
> Memory renaming позволяет **процессору** тайно держать её в регистре, не нарушая `volatile`.  
> Компилятор думает, что идёт в память. Процессор делает вид, что память — это регистр.


### 1. Что делает `volatile`

`volatile` говорит компилятору:

> «Не держи эту переменную в регистре. Каждый раз, когда с ней работаешь, честно читай её из памяти и честно записывай обратно».

Для xorshift-цикла это значит, что вместо условно такого:

```asm
xor rax, rax
shl rax, 13
...
```

компилятор делает примерно так:

```asm
mov rax, [x]   ; прочитал x из памяти
xor rax, ...
mov [x], rax   ; записал x в память
mov rax, [x]   ; снова прочитал x
...
```

То есть на каждом шаге — load → ALU → store по одному и тому же адресу.

### 2. Почему это обычно медленно

Даже если переменная лежит в L1-кэше, это не регистр.

Когда ты только что записал значение в память и сразу читаешь его обратно, процессор умеет делать **store-to-load forwarding**: не ждёт, пока значение доедет до L1, а пересылает его из store buffer в load. Но это всё равно стоит несколько циклов — на Skylake порядка 4–5.

В цикле xorshift таких пар «записал → прочитал» три за раунд. 10 000 раундов — и эти 5 циклов начинают заметно тормозить.

### 3. Что такое memory renaming

Представь, что память — это доска с числами, а регистры — карманы. Обычно `volatile` заставляет каждый раз идти к доске: прочитал, посчитал, записал.

Memory renaming — это умный секретарь у доски. Он замечает:

> «Ты только что записал на строку `x` число 42. А теперь сразу читаешь ту же строку `x`. Зачем идти к доске? Я запомнил, что там 42. Вот, держи из кармана».

Технически процессор распознаёт паттерн:

```text
load x → ALU → store x
load x → ALU → store x
load x → ALU → store x
...
```

и на время «переименовывает» адрес `x` в физический регистр. Для конвейера это выглядит так, будто переменная всё время жила в регистре:

- load `x` = прочитать физический регистр;
- store `x` = записать в физический регистр;
- реальная память обновляется позже или когда это действительно нужно.

Задержка load становится фактически нулевой. Процессор не платит те самые 5 циклов store-to-load forwarding.

### 4. Почему на Ryzen разница исчезла

На Zen 5 memory renaming ловит этот паттерн. Компилятор всё ещё вставляет `load`/`store`, потому что видит `volatile`, но процессор их «отменяет» внутри себя. Цикл упирается уже не в память, а в ALU и счётчик.

На Skylake такого механизма нет. Там каждый `load` после `store` по тому же адресу платит полную цену forwarding'а. Поэтому `volatile`-версия и тормозила в 3 раза.

### 5. Почему C, Rust и Go сошлись

Потому что все три теперь измеряют примерно одно и то же:

- C + `volatile` — компилятор формально ходит в память, но CPU это прячет;
- Rust + `black_box` — компилятор не оптимизирует, но память не трогается так агрессивно;
- Go-контроль — вообще без C.

Все упираются в ALU + накладные расходы вызова. Отсюда 12 007 / 12 073 / 11 914 нс — разница в пределах шума.

### 6. Важная оговорка

Memory renaming помогает **только на узком паттерне**: один и тот же адрес, цепочка load → ALU → store, нет алиасинга, нет гонок, прерывания не ломают поток.

Если адресов много, если другой поток пишет в ту же память, если паттерн сложный — renaming не сработает. `volatile` всё ещё нужен для семантики, и в других случаях он всё ещё может тормозить.
